# WARP через Xray с AmneziaWG-обфускацией

Перенос рабочего конфига AmneziaWG (Cloudflare WARP) на ядро Xray с сохранением обфускации,
которая обходит блокировку WireGuard российским ТСПУ. Результат подтверждён живым A/B тестом
(см. раздел «Результаты A/B теста»).

## Что это и зачем

Исходная точка — `WARPv3_77.conf`: конфиг Cloudflare WARP в формате AmneziaWG (AWG). Он работает
в сетях, где чистый WireGuard режется ТСПУ, потому что AWG добавляет к WireGuard junk-пакеты,
которые ломают сигнатурную детекцию.

Задача: получить тот же результат на ядре Xray, чтобы:

- пользоваться одним ядром для всего (Xray уже используется для других протоколов);
- импортировать профиль в клиенты на ядре Xray (v2rayTun, Throne, Happ, Hiddify);
- не тащить отдельный клиент AmneziaWG.

Итог — `warp-xray.json` (полный конфиг с локальными inbound'ами) и `warp-xray-client.json`
(тот же профиль без inbound'ов, для импорта в клиент).

## Почему нельзя просто перенести конфиг

Xray **не поддерживает** поля AmneziaWG. Проверка бинаря Xray 26.3.27: строк `jc`, `jmin`, `jmax`,
`s1`, `s2`, `h1`..`h4`, `i1`, `itime`, `junk` — **0 вхождений**. Wireguard-аутбаунд Xray — это
обычный WireGuard, без AWG-расширений. Единственный механизм генерации мусорного трафика в
Xray — поле `noises` у аутбаунда `freedom`.

### Важное предупреждение про `xray run -test`

JSON-парсер Xray **нестрогий и молча игнорирует неизвестные ключи**. Проверка: в конфиг было
добавлено заведомо несуществующее поле

```json
"zzz_fake_field_12345": 777
```

и `xray run -test` ответил `Configuration OK`.

Отсюда практический вывод: **успешный `-test` НЕ доказывает, что поле поддерживается.**
Если дописать в wireguard-аутбаунд `"jc": 4, "jmin": 40, "jmax": 70`, конфиг тоже пройдёт проверку —
и при этом не отправит ни одного junk-пакета. Многие «AWG-конфиги для Xray» из интернета устроены
именно так и не работают, хотя валидируются.

Исключение, подтверждающее правило: `noises` валидацию поля `type` **делает**. На `"type": "bogusType"`
Xray отвечает ошибкой:

```
Invalid packet, only rand/str/hex/base64 are supported
```

Допустимы только `rand`, `str`, `hex`, `base64`. Благодаря `hex` пакеты I1/I2 удалось воспроизвести
байт-в-байт.

## Как устроен обход

В исходном AWG-конфиге:

- `H1..H4` = 1, 2, 3, 4 — это значения **по умолчанию**, то есть типы WireGuard-пакетов не подменяются;
- `S1..S4` = 0 — то есть заголовки handshake-пакетов **не удлиняются**.

Значит, сами WireGuard-пакеты не модифицируются вообще. Вся обфускация — это **junk-пакеты,
отправляемые перед handshake'ом**:

| Параметр AWG | Что это | Соответствие в Xray |
|---|---|---|
| `I1` | 348 байт, SIP-запрос `INVITE sip:bob@biloxi.com SIP/2.0` | `noises[0]`, `type: "hex"`, тот же hex байт-в-байт |
| `I2` | 245 байт, SIP-ответ `SIP/2.0 100 Trying` | `noises[1]`, `type: "hex"`, тот же hex байт-в-байт |
| `Jc` = 4 | 4 случайных junk-пакета | 4 записи `noises` с `type: "rand"` |
| `Jmin` = 40, `Jmax` = 70 | размер случайных пакетов, байт | `packet: "40-70"` у каждой из 4 записей |
| `S1`..`S4` = 0 | удлинение заголовков отключено | воспроизводить не требуется |
| `H1`..`H4` = 1,2,3,4 | значения по умолчанию, подмены нет | воспроизводить не требуется |
| `MTU` = 1420 | | `settings.mtu` у wireguard-аутбаунда |
| `PrivateKey` / peer `PublicKey` / `Endpoint` / `Address` | | `secretKey` / `peers[].publicKey` / `peers[].endpoint` / `address` |
| `DNS` | | секция `dns.servers` |

**Механизм.** I1 и I2 — не случайный мусор, а валидные SIP-сообщения: запрос `INVITE` и ответ
`100 Trying` из примера RFC 3261. ТСПУ видит на UDP-флоу сначала SIP-диалог, классифицирует
5-tuple как VoIP-сессию и снимает с него WireGuard-детектор. Дальше по этому же сокету идёт
настоящий WireGuard-handshake — и проходит.

Именно поэтому перенос на Xray вообще оказался возможен: всё, чего требует этот конкретный
профиль обфускации, — отправить несколько произвольных UDP-пакетов перед handshake'ом. Ровно это
и умеет `noises`. Профили AWG, где `S1..S4` или `H1..H4` отличны от дефолта, на Xray
перенести **нельзя** — модификации самих WireGuard-пакетов ядро не умеет.

## Архитектура конфига

Xray не умеет отправлять noise «изнутри» wireguard-аутбаунда. Поэтому wireguard-аутбаунд
подключается не напрямую, а через `freedom`-аутбаунд с `noises`, который и создаёт UDP-сокет.
Связка — `streamSettings.sockopt.dialerProxy`.

```
приложение
    |
    v
[socks-in 127.0.0.1:10808]  /  [http-in 127.0.0.1:10809]
    |
    v
routing: весь tcp,udp -> "warp"
    |
    v
+---------------------------------------+
| outbound "warp"  (protocol: wireguard) |
|   secretKey, address, mtu 1420         |
|   peer 8.6.112.7:946                   |
|   streamSettings.sockopt.dialerProxy   |----+
+---------------------------------------+    |
                                              v
                    +--------------------------------------------+
                    | outbound "noise-out"  (protocol: freedom)   |
                    |   noises:                                   |
                    |     hex I1  (SIP INVITE, 348 B)   delay 1-2 |
                    |     hex I2  (SIP 100 Trying, 245 B) delay 1-2 |
                    |     rand 40-70  x4                delay 1-5 |
                    +--------------------------------------------+
                                              |
                                              v
                                    UDP -> 8.6.112.7:946
```

Порядок на проводе: сначала уходят 6 noise-пакетов (2 SIP + 4 случайных), затем по тому же
сокету — WireGuard-handshake и весь дальнейший трафик.

## Результаты A/B теста

Условия: VPN пользователя выключен (интерфейса `throne-tun` нет, `ip rule` чистый), поэтому тест
валиден. Оба варианта используют одни и те же креды и один и тот же endpoint. **Единственное
различие A и B — наличие `noises`.**

| Показатель | A: с обфускацией | B: контроль, чистый WireGuard |
|---|---|---|
| Итог | **РАБОТАЕТ** | **ПРОВАЛ** |
| `cdn-cgi/trace` | `warp=on` | нет ответа |
| Успешных HTTP-запросов | 9/9 за 161 с | 0/4, все `http=000` (таймаут, `rc=28`) |
| Handshake'ов отправлено / ответов | 2 / 2 | 10 / 1 |
| Разрывы | нет | `Handshake did not complete` — 8 раз |
| Рехендшейк (~2 мин) | пережит | `Retrying handshake because we stopped hearing back after 15 seconds` |
| Задержка | 49 мс (среднее по 5) | — |
| Скорость | 53.9 Мбит/с (6.42 MB/s, 9.5 МБ за 1.49 с) | — |
| UDP через SOCKS | OK | — |
| IPv6 | OK | — |

**Вывод.** В варианте B первый handshake **прошёл** — Cloudflare на него ответил за 95 мс. Значит,
креды и endpoint валидны, и Cloudflare тут ни при чём. После этого ответы прекратились полностью:
ТСПУ пропускает первый пакет, опознаёт по нему сигнатуру WireGuard и режет флоу по 5-tuple.
Обфускация не «желательна», а **обязательна**, и перенесённая на Xray версия её действительно
воспроизводит.

### Известное ограничение

Xray отправляет noise-пакеты **один раз при создании UDP-сокета**, а AmneziaWG — **перед каждым
handshake'ом**. На дистанции теста (161 с, один рехендшейк) это проблем не создало: рехендшейк
прошёл без повторной отправки noise, флоу уже был классифицирован как VoIP. Многочасовая
стабильность **не проверялась** — возможно, что при длительной сессии или пересоздании сокета
поведение будет другим.

## Как пользоваться

### Нативный Xray

Запуск:

```sh
xray run -c ./warp-xray.json
```

Проверка конфига без запуска (помня про нестрогий парсер — см. выше):

```sh
xray run -test -c ./warp-xray.json
```

Проверка, что трафик идёт через WARP:

```sh
curl -x socks5h://127.0.0.1:10808 https://www.cloudflare.com/cdn-cgi/trace
```

В ответе должно быть `warp=on`. Обратите внимание: URL **без** завершающего слеша — на
`.../trace/` Cloudflare отдаёт 404.

HTTP-прокси доступен на `127.0.0.1:10809`.

Остановка — `Ctrl+C`, либо, если запущен в фоне:

```sh
pkill -f 'xray run -c ./warp-xray.json'
```

### Импорт в клиенты (v2rayTun, Throne, Happ, Hiddify)

Используйте `warp-xray-client.json` — это тот же профиль без секции `inbounds`
(проверено: Xray 26.3.27 принимает конфиг без `inbounds` — `Configuration OK`, и стартует с ним:
`core: Xray 26.3.27 started`). Клиент подставляет свой inbound / tun сам; если конкретный клиент
всё же требует inbound, добавьте socks на `127.0.0.1:10808` — большинство клиентов такой inbound
всё равно переопределяют.

Два важных условия:

1. **Импортировать нужно именно JSON, а не share-ссылку.** Формат `wireguard://` не умеет
   переносить произвольные бинарные junk-пакеты: hex-строки I1/I2 (348 и 245 байт) в него не
   укладываются. При импорте по ссылке обфускация потеряется и останется чистый WireGuard —
   то есть вариант B из теста выше, который не работает.
2. **Ядро клиента должно поддерживать `noises`** у `freedom`-аутбаунда и `sockopt.dialerProxy`.
   Это относительно свежая функциональность Xray; на старом ядре конфиг импортируется, ошибки
   не покажет (парсер нестрогий), но noise отправляться не будет. Признак проблемы тот же, что
   у варианта B: первый handshake проходит, дальше тишина.

## Файлы репозитория

| Файл | Что это |
|---|---|
| `WARPv3_77.conf` | исходный рабочий AmneziaWG-конфиг, эталон для переноса |
| `warp-xray.json` | итоговый рабочий конфиг Xray: socks 10808 + http 10809, wireguard-аутбаунд через `dialerProxy` на freedom с `noises` |
| `warp-xray-client.json` | тот же профиль без `inbounds` — для импорта в клиенты на ядре Xray |
| `legacy-xray-profile-INVALID.json` | предыдущая неудачная попытка, **нерабочая**, оставлена как антипример (см. ниже) |
| `test-warp.sh` | скрипт A/B теста |
| `test-report.txt` | отчёт последнего прогона теста |
| `xray-A.log` | лог Xray, вариант A (с обфускацией) |
| `xray-B.log` | лог Xray, вариант B (контроль, чистый WireGuard) |
| `xray.log` | лог первого, забракованного прогона |

Логи в репозитории **отфильтрованы** перед публикацией: оставлены только события старта ядра и
транспорта/handshake'а WireGuard, все построчные записи о конкретных соединениях удалены. Счётчики
handshake'ов, на которых строятся выводы ниже, сохранены полностью.

### Про `legacy-xray-profile-INVALID.json`

Это ранняя попытка конфига (695 строк, те же WARP-креды). Отличия от рабочего варианта:

| | legacy (не работает) | `warp-xray.json` (работает) |
|---|---|---|
| Количество noise-пакетов | 120 | 6 |
| Тип пакетов | все `rand` | 2 × `hex` (I1/I2) + 4 × `rand` |
| Размер `rand`-пакетов | `23-911` | `40-70` |
| MTU | 1280 | 1420 |
| SIP-пакеты I1/I2 | **нет** | есть |

Почему не годится: без I1/I2 нет поддельной SIP-сессии, а именно на ней держится обход. 120
случайных пакетов размером 23–911 байт — это просто мусор, который ТСПУ ни за что не принимает;
WireGuard-детектор с флоу не снимается. Плюс параметры разошлись с эталонным AWG-конфигом
(размеры junk'а и MTU взяты произвольно, а не из `WARPv3_77.conf`). Файл сохранён именно как
пример того, как делать не надо.

## Воспроизведение тестов

```sh
./test-warp.sh          # прогнать A/B, в конце погасить оба инстанса
./test-warp.sh --keep   # оставить жить только инстанс A (B гасится всегда)
```

Скрипт:

- проверяет, что VPN пользователя выключен (иначе тест невалиден) и что порты 10808/10809/10818/10819 свободны;
- генерирует конфиг B программно из `warp-xray.json`, вырезая `dialerProxy` и `noises`, — креды в скрипте не хардкодятся;
- временный конфиг B кладёт в `${TMPDIR:-/tmp}/warp-noobf.json`; каталог можно переопределить переменной `SCRATCH_DIR`;
- поднимает A (socks 10808) и B (socks 10818), гоняет через них curl, считает handshake'и в логах;
- пишет всё в stdout и в `test-report.txt` (перезаписывается при каждом запуске), логи Xray — в `xray-A.log` и `xray-B.log`.

Не требует sudo и не трогает маршруты, `nft`, `iptables` и `ip rule`.

## Замечание о приватности опубликованных логов

WARP-креды, параметры обфускации, адреса Cloudflare и локальные адреса оставлены как есть
осознанно. Публичные IP-адреса сторонних сервисов, попавшие в debug-логи (это адреса назначения
пользовательского трафика во время теста), заменены на `<redacted-ip>`. Временные пути заменены
на `<tmp>`, имя хоста — на `<host>`.
