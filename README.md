# WARP через Xray с обфускацией в стиле AmneziaWG

Перенос рабочего конфига AmneziaWG (подключение к Cloudflare WARP) на ядро Xray с сохранением
обфускации, которая обходит блокировку WireGuard российским ТСПУ.

Репозиторий — это не только готовый конфиг, но и протокол исследования: что именно проверялось,
какими цифрами, что сработало и, главное, что **не** сработало и почему. Вторая часть обычно
полезнее первой, потому что рабочий рецепт со временем сломается, а понимание — нет.

---

## 1. Задача

Исходная точка — конфиг Cloudflare WARP в формате AmneziaWG (AWG). Он работает в сетях, где
чистый WireGuard режется ТСПУ: AWG подмешивает к сессии junk-пакеты, которые ломают сигнатурную
детекцию.

Нужно получить тот же результат на ядре Xray, чтобы:

- пользоваться одним ядром для всего (Xray уже используется для других протоколов);
- импортировать профиль в мобильные клиенты на ядре Xray (v2rayTun, Throne, Happ, Hiddify);
- не тащить отдельный клиент AmneziaWG.

## 2. Краткий итог

Перенос возможен и работает. Готовые конфиги в корне репозитория:

| файл | для чего |
|---|---|
| `warp-xray-megafon.json` | **рабочий на мобильной сети (Мегафон)**, с локальными inbound'ами |
| `warp-xray-megafon-client.json` | то же без `inbounds` — для импорта в клиент |
| `warp-xray.json` | первый перенос, SIP-профиль; проверен на проводном, на мобильной НЕ работает |
| `warp-xray-client.json` | то же без `inbounds` |

Рецепт, который дал `warp=on` на Мегафоне:

| параметр | значение | почему именно так |
|---|---|---|
| endpoint | `162.159.192.1:500` | единственный, который прошёл; `:2408` на том же адресе — нет |
| MTU | `1280` | при `1420` хендшейк проходит, но данные не идут |
| noise #1 | `hex` = копия настоящего QUIC Initial, 1252 байта | синтетический «похожий на QUIC» пакет не работает |
| noise #2..#9 | 8 × `rand`, размер `23-911`, задержка `1-3` | соответствует `Jc=120`, `Jmin=23`, `Jmax=911` из AWG |
| keepAlive | `5` | как persistent keepalive у AWG |
| ключ | любой живой | фактор ключа проверен и исключён |

Измеренные цифры этого варианта: первый запрос 0.39 с, стабильность 5/5 запросов за ~100 с,
хендшейк — одна инициация, один ответ.

Схема связки в Xray:

```
приложение
    │  SOCKS 127.0.0.1:10808 / HTTP 127.0.0.1:10809
    ▼
outbound "warp"   (protocol: wireguard, MTU 1280, endpoint 162.159.192.1:500)
    │  streamSettings.sockopt.dialerProxy = "noise-out"
    ▼
outbound "noise-out"  (protocol: freedom)
    │  перед первым байтом сессии шлёт noises:
    │    1 × hex   — настоящий QUIC Initial (1252 б)
    │    8 × rand  — мусор 23..911 байт с задержкой 1..3 мс
    ▼
UDP → Cloudflare WARP
```

## 3. Почему нельзя просто перенести AWG-конфиг

Xray **не поддерживает** поля AmneziaWG. Проверка бинаря Xray 26.3.27: строк `jc`, `jmin`, `jmax`,
`s1`, `s2`, `h1`..`h4`, `i1`, `itime`, `junk` — **0 вхождений**. Wireguard-аутбаунд Xray — это
обычный WireGuard, без AWG-расширений. Единственный механизм генерации мусорного трафика в Xray —
поле `noises` у аутбаунда `freedom`.

### Предупреждение: `xray run -test` ничего не доказывает

JSON-парсер Xray **нестрогий и молча глотает неизвестные ключи**. Проверка: в конфиг добавили
заведомо несуществующее поле

```json
"zzz_fake_field_12345": 777
```

и `xray run -test` ответил `Configuration OK`.

Практический вывод: **успешный `-test` НЕ доказывает, что поле поддерживается.** Если вы нашли в
интернете «конфиг Xray с полями Jc/Jmin/Jmax» и он проходит `-test` — это ничего не значит, поля
просто выброшены при разборе. Единственная проверка — реальный трафик.

Обратный пример, показывающий, что `noises` действительно разбирается: поле `type` валидируется.
На `"type": "bogusType"` Xray отвечает

```
Invalid packet, only rand/str/hex/base64 are supported
```

Именно `type: "hex"` позволил воспроизводить junk-пакеты AWG байт-в-байт.

## 4. Как устроена обфускация: AWG → Xray

| поле AWG | что делает | эквивалент в Xray |
|---|---|---|
| `I1`, `I2` | отправить конкретный пакет до хендшейка | `noises: [{"type":"hex","packet":"<hex>"}]` |
| `Jc` | сколько junk-пакетов слать | количество элементов `{"type":"rand"}` |
| `Jmin`/`Jmax` | диапазон размера junk-пакета | `"packet": "Jmin-Jmax"` |
| `S1`..`S4` | добавить junk внутрь самих WG-пакетов хендшейка | **нет эквивалента** |
| `H1`..`H4` | подменить типы сообщений WireGuard | **нет эквивалента** |
| `MTU` | MTU интерфейса | `settings.mtu` у wireguard-аутбаунда |
| `Endpoint` | адрес пира | `peers[0].endpoint` |

Отсутствие `S1`..`S4` и `H1`..`H4` в данном случае не помешало: во всех образцах, с которыми
велась работа, `H1-H4 = 1,2,3,4` (то есть дефолт, подмены нет), а `S1..S4 = 0` (внутрь WG-пакетов
ничего не добавляется). **Вся обфускация в этих конфигах живёт в junk-пакетах**, а их Xray умеет
воспроизводить точно.

Если бы в конфиге были ненулевые `S`/`H`, перенести его на Xray было бы невозможно.

### Главное открытие: `I1` — это QUIC Initial

Разбор четырёх эталонных AWG-конфигов (`awg-samples/`) показал, что у всех работавших образцов
`I1` — **структурно валидный QUIC Initial v1**, а у неработавшего — текстовый SIP.

| образец | первый байт | version | DCID | размер | вывод |
|---|---|---|---|---|---|
| `megafon-ok-1180.conf` | `0xc7` | `0x00000001` | 8 б | 1250 б | QUIC Initial v1 |
| `megafon-ok-903.conf` | `0xce` | `0x00000001` | 8 б | 1250 б | QUIC Initial v1 |
| `megafon-ok-500-jc120.conf` | `0xc2` | `0x00000001` | 20 б | 1252 б | QUIC Initial v1 |
| `megafon-fail-946-sip.conf` | `0x49` (`'I'`) | `0x4e564954` = ASCII `NVIT` | — | 348 б | SIP INVITE, не QUIC |

У всех QUIC-образцов сходится `length`-varint: объявленная длина совпадает с фактическим числом
байт после неё (например, у `ok-500`: заявлено 1222, фактически 1222). Это не случайный мусор,
похожий на QUIC, а настоящие перехваченные пакеты.

То есть рабочая обфускация маскирует начало сессии под **HTTP/3-соединение браузера**, а не под
VoIP-звонок. Разница принципиальна — см. раздел 7.

## 5. Хронология: что проверялось и чем кончилось

### Этап 1. Что умеет Xray 26.3.27

Разобрано выше (раздел 3). Итог: архитектура переноса — outbound `wireguard` со
`streamSettings.sockopt.dialerProxy`, указывающим на outbound `freedom` с `noises`.

### Этап 2. Первый перенос (SIP-профиль) и A/B тест на проводном

Исходный AWG-конфиг (`legacy/WARPv3_77.conf`): `H1-H4 = 1,2,3,4`, `S1-S4 = 0`,
`I1` = SIP INVITE из RFC 3261 (348 б), `I2` = SIP 100 Trying (245 б), `Jc=4`, `Jmin=40`, `Jmax=70`.
Перенесён в `warp-xray.json`.

A/B тест на проводном соединении (`tests/test-warp.sh`, отчёт `results/test-report.txt`):

| | вариант A — с `noises` | вариант B — тот же конфиг без `noises` |
|---|---|---|
| результат | `warp=on` | ни одного ответа |
| запросы | 9/9 успешных за 161 с | все curl — таймаут |
| разрывы | нет | — |
| хендшейки | 2 отправлено / 2 ответа | 10 отправлено / 1 ответ |
| `Handshake did not complete` | 0 | 8 раз |
| задержка | 49 мс | — |
| скорость | 53.9 Мбит/с (9.5 МБ за 1.49 с) | — |

Первый хендшейк B прошёл за 95 мс, после чего пошло
`Retrying handshake because we stopped hearing back after 15 seconds`.

Вывод этапа: на проводном ТСПУ действительно режет чистый WireGuard, обфускация необходима,
и SIP-профиль в Xray её воспроизводит.

**Урок про методику.** В первом прогоне URL проверки был записан как
`https://www.cloudflare.com/cdn-cgi/trace/` — с завершающим слешем Cloudflare отдаёт 404, из-за
чего 16 фактически успешных запросов были помечены как FAIL. Правильный URL — без слеша. Прежде
чем делать выводы из красной таблицы, стоит проверить сам измеритель.

### Этап 3. Провал на мобильной сети и матрица из 10 вариантов

Тот же `warp-xray.json` на Мегафоне (тетеринг iPhone) не работает вообще.

Пользователь предоставил четыре эталонных AWG-конфига (`awg-samples/`), три из которых у него
когда-то работали на Мегафоне, а четвёртый — нет. Именно их разбор дал открытие про QUIC
(раздел 4).

Матричный тест из 10 вариантов (`tests/test-megafon.sh`, отчёт `results/megafon-report.txt`):
**OK получил ровно один вариант** — QUIC-`I1` из `ok-500` + 8 × rand `23-911` +
endpoint `162.159.192.1:500` + MTU 1280 + ключ `IFkdR`. Остальные девять — FAIL.

Значимая пара из этого прогона: вариант 9 (с QUIC-пакетом) = OK, вариант 10 (тот же конфиг, только
8 × rand без hex-пакета) = FAIL. Дело не в объёме мусора, а именно в QUIC-пакете.

### Этап 4. Ретест с изоляцией переменных

Проблема матрицы из этапа 3 — в ней менялось по несколько параметров сразу. Ретест
(`tests/retest-megafon.sh`, отчёт `results/retest-report.txt`) построен так, что каждый вариант
отличается от базы **ровно одним параметром**.

Сначала из уравнения убран ключ: все три имеющиеся регистрации WARP (`p1Fqp`, `IFkdR`, `WE7c0`)
проверены на рабочей сети и все три дали `warp=on`. Фактор «мёртвый ключ» исключён.

**Доступность endpoint'ов на голом WireGuard без обфускации** (Мегафон, 5 адресов, один ключ,
один MTU): FAIL у всех пяти, но **двумя разными способами**:

| endpoint | хендшейк отпр./получ. | что это значит |
|---|---|---|
| `162.159.192.1:500` | 4 / 0 | UDP до пира вообще не доходит (или ответ режется) |
| `162.159.192.1:2408` | 4 / 0 | то же |
| `8.6.112.7:946` | 2 / 1 | хендшейк ПРОШЁЛ, душится уже установленная сессия |
| `8.34.146.7:1180` | 2 / 1 | то же |
| `8.34.70.4:903` | 2 / 1 | то же |

Это различие важно: «ответа на хендшейк нет» и «ответ есть, но данные не идут» — два разных
механизма блокировки, и путать их нельзя. Отсюда же следует, что **ответ на хендшейк сам по себе
ничего не доказывает** — критерий успеха только один: получен ли `warp=on`.

**Матрица с изоляцией.** База = QUIC-`I1` из `ok-500` + 8 × rand `23-911` + `162.159.192.1:500` +
MTU 1280:

| вариант | отличие от базы | результат | хендшейк | время |
|---|---|---|---|---|
| 3.1 (база) | — | **OK**, `warp=on` | 1 / 1 | 0.39 с |
| 3.2 | только порт: `:500` → `:2408` | FAIL | 4 / 0 | таймаут |
| 3.4 | только hex: чужой `I1` → свой синтетический QUIC | FAIL | 4 / 0 | таймаут |
| 3.5 | только hex: QUIC → SIP (RFC 3261) | FAIL | 4 / 0 | таймаут |
| 3.6 | только MTU: 1280 → 1420 | FAIL | 1 / 1 | таймаут |
| 3.3 | полная реплика `ok-1180` (ep `8.34.146.7:1180`, MTU 1420) | FAIL | 1 / 1 | таймаут |

Стабильность варианта 3.1: 5 запросов из 5 за ~100 с, время ответа от 0.24 до 0.79 с, отложенного
среза не видно.

### Этап 5. Почему синтетический QUIC не работает

Вариант 3.4 отличается от рабочей базы только тем, что вместо копии настоящего `I1` подставлен
свой сгенерированный пакет — структурно безупречный QUIC Initial v1 (правильный первый байт,
`version = 0x00000001`, корректный DCID, `length`-varint сходится с фактическим размером, общий
размер 1250 байт). И он не работает: 4 инициации, 0 ответов.

Причина в устройстве QUIC. Ключи шифрования QUIC Initial выводятся **из DCID по фиксированному
публичному алгоритму** (RFC 9001): DPI видит DCID в открытом виде, выводит те же ключи и
расшифровывает Initial-пакет, а внутри должен лежать валидный TLS ClientHello. Пакет со случайным
payload эту проверку не проходит, и флоу режется сразу — отсюда 4/0, то есть блокировка ещё
до хендшейка.

Настоящий `I1` содержит валидный зашифрованный ClientHello и проверку проходит.

Из этого следуют два практических правила:

- генерировать «похожий на QUIC» пакет из случайных байт **бесполезно**, нужен настоящий
  QUIC Initial;
- **DCID в готовом пакете менять нельзя** — от него зависят ключи, и правка DCID превращает
  валидный пакет в невалидный.

### Этап 6. Нативный AmneziaWG на Мегафоне — базовая истина

Чтобы понять, виноват ли перенос на Xray, те же образцы подняты родным `awg-quick`
(`tests/retest2.sh`).

Два фальстарта по системным причинам, оба — не про сеть:

1. `Error: ipv6: IPv6 is disabled on this device` — в системе отключён IPv6, а в конфигах есть
   v6-адрес. Обход: из временной копии удаляются IPv6 в `Address`, IPv6 в `DNS` и `::/0` в
   `AllowedIPs`.
2. `resolvconf: signature mismatch: /etc/resolv.conf` — конфликт с системным resolvconf.
   Обход: строка `DNS` удаляется из временной копии.

Результат нативного AmneziaWG на Мегафоне (`results/retest2-report.txt`):

| конфиг | нативный AWG | Xray-реплика |
|---|---|---|
| `megafon-ok-1180.conf` | FAIL | FAIL (вариант 3.3) |
| `megafon-ok-903.conf` | FAIL | не тестировался отдельно |
| `megafon-ok-500-jc120.conf` | **OK**, `warp=on` | **OK** (вариант 3.1) |

**Ключевой вывод: Xray-реплики ведут себя точно так же, как оригиналы в родном AmneziaWG.**
Дефекта переноса AWG → Xray нет. Конфиги на `8.34.x` просто умерли с того момента, когда
пользователь их последний раз проверял; провал этапа 3 объясняется состоянием сети, а не качеством
конвертации.

Отдельно проверено, что рабочий рецепт не привязан к ключу из образца: с рабочим профилем на
Мегафоне и `IFkdR`, и основной ключ `p1Fqp` дают `warp=on`, хендшейк 1/1 у обоих
(`results/retest2-IFkdR-control.log`, `results/retest2-p1Fqp-test.log`). Именно поэтому прод-конфиг
собран на `p1Fqp`.

### Этап 7. Откуда взялся рабочий пакет

Конфиг `megafon-ok-500-jc120.conf` получен генератором
`https://raw.githubusercontent.com/ImMALWARE/bash-warp-generator/main/warp_generator.sh`.
Разбор скрипта:

- он генерирует пару ключей (`wg genkey`) и регистрирует устройство в Cloudflare API
  (`api.cloudflareclient.com/v0i1909051800`: `POST /reg` с `type: ios`, затем
  `PATCH reg/<id>` с `warp_enabled: true`);
- **но `I1` и `Endpoint = 162.159.192.1:500` захардкожены константами**, а строка, которая брала
  endpoint из ответа API, закомментирована.

Отсюда:

- все конфиги от этого скрипта имеют **один и тот же** QUIC-пакет и **один и тот же** endpoint;
  перегенерация даёт свежие креды, но не новый `I1`;
- образцы `ok-1180` и `ok-903` (другой `I1`, DCID 8 байт, адреса `8.34.x`) получены **другим**
  источником, который endpoint из API всё-таки читал.

**Риск.** Этот `I1` — публичная константа массового скрипта. Когда ТСПУ занесёт её в сигнатуры,
профиль отвалится разом у всех — ровно так, как уже случилось с SIP-пакетами из RFC 3261, которые
тоже были публичным примером из документа.

**План на будущее (не реализован).** Снять свой настоящий QUIC Initial дампом: `tcpdump` +
`curl --http3` (curl в системе собран с ngtcp2/nghttp3, HTTP/3 доступен), взять первый исходящий
UDP-пакет целиком и подставить его вместо константы. Внутри будет валидный зашифрованный
ClientHello с реальным SNI, то есть пакет, которого нет ни в одной сигнатурной базе. Менять в нём
после снятия нельзя ничего, включая DCID.

## 6. Что влияет, а что нет

| фактор | влияет | доказательство |
|---|---|---|
| ключ / регистрация WARP | **нет** | все три ключа дают `warp=on`; рабочий профиль работает и на `IFkdR`, и на `p1Fqp` |
| endpoint и порт | **да** | `:500` = OK, `:2408` на том же адресе = FAIL (3.1 vs 3.2) |
| MTU | **да** | 1280 = OK, 1420 = FAIL при всём прочем равном (3.1 vs 3.6) |
| профиль пакета (`I1`) | **да** | QUIC = OK, SIP = FAIL, свой синтетический QUIC = FAIL (3.1 vs 3.5 vs 3.4) |
| наличие обфускации вообще | **да** | голый WG на том же endpoint = FAIL (1.1), с QUIC-обфускацией = OK (3.1) |
| объём rand-мусора | сам по себе нет | 8 × rand без hex-пакета = FAIL (вариант 10 этапа 3) |

Все три «да» должны совпасть одновременно: правильный endpoint с правильным портом, MTU 1280 и
конкретный настоящий QUIC-пакет. Любого одного из них достаточно, чтобы всё сломать.

## 7. Как пользоваться

### Нативный Xray на десктопе

```sh
# проверить конфиг (ничего не запускает)
xray run -test -c ./warp-xray-megafon.json

# запустить
xray run -c ./warp-xray-megafon.json

# проверить в другом терминале, что трафик идёт через WARP
curl -s -x socks5h://127.0.0.1:10808 https://www.cloudflare.com/cdn-cgi/trace
# ожидается строка warp=on

# остановить
# Ctrl+C в терминале с xray, либо:
pkill -f 'xray run -c .*warp-xray-megafon.json'
```

Прокси после запуска: SOCKS5 на `127.0.0.1:10808` (с UDP), HTTP на `127.0.0.1:10809`.

**Важно:** URL проверки — без завершающего слеша. На `.../cdn-cgi/trace/` Cloudflare отдаёт 404.

### Импорт в мобильные клиенты

Используйте `warp-xray-megafon-client.json` — это тот же профиль без секции `inbounds`, локальные
слушатели клиент подставляет сам. Такой конфиг Xray принимает (проверено).

Два ограничения:

1. **Нужен именно JSON, а не share-ссылка.** Обфускация держится на hex-пакете размером 1252 байта,
   а формат `wireguard://` его никуда не укладывает. Клиент должен уметь импортировать сырой
   JSON-конфиг Xray.
2. **Ядро клиента должно поддерживать `noises` у freedom-аутбаунда.** Если не поддерживает, конфиг
   импортируется без ошибок (парсер нестрогий, см. раздел 3), просто обфускации не будет — и
   соединение не заработает там, где режут WireGuard.

## 8. Честные ограничения

- **Рабочий рецепт проверен на одной сети** — Мегафон через тетеринг iPhone. На других операторах
  и в других регионах результат может отличаться: ТСПУ настраивают по-разному.
- **Профиль QUIC + `:500` + MTU 1280 не проверялся на проводном и WiFi.** На проводном проверялся
  только старый SIP-профиль (`warp-xray.json`), и он там работал. Обратное тоже верно: SIP-профиль
  на мобильной сети не работает.
- **Долговременная стабильность не проверялась.** Максимум — около 161 с на проводном (этап 2) и
  около 100 с на мобильной (этап 4). Как профиль ведёт себя часами, через десятки рехендшейков,
  неизвестно.
- **Выводы про блокировку целых подсетей сделаны по выборке из трёх адресов** (`8.6.112.7`,
  `8.34.146.7`, `8.34.70.4`). Это мало: возможно, дело в конкретных адресах, а не в подсетях
  `8.6.x`/`8.34.x` целиком.
- **Рабочий `I1` — чужой пакет и публичная константа.** См. этап 7: это известный риск, а не
  надёжное решение.
- Причина, по которой MTU 1420 ломает передачу при рабочем хендшейке, не установлена. Похоже на
  срез по размеру пакета или на проблему фрагментации в мобильной сети, но прямо это не измерялось.

### Как воспроизвести тесты

Скрипты запускаются из корня репозитория и сами переходят в него, где бы вы их ни вызвали:

```sh
./tests/test-warp.sh          # A/B: обфускация против её отсутствия
./tests/test-megafon.sh       # матрица из 10 профилей
./tests/retest-megafon.sh     # матрица с изоляцией переменных (нужен sudo для этапа нативного AWG)
./tests/retest2.sh            # нативный awg-quick; --awg-only пропускает Xray-часть
```

Каждый скрипт перезаписывает свой отчёт в `results/` и кладёт туда же отфильтрованные логи.
Сырые debug-логи остаются в `/tmp` и в репозиторий не попадают: они содержат домены и коннекты
пользователя. Логи в `results/` отфильтрованы по белому списку — только старт ядра и события
WireGuard (хендшейки, keepalive, ошибки транспорта).

Требуется: `xray` (проверялось на 26.3.27), `curl`, `python3`, для нативных тестов —
`amneziawg-tools` (`awg-quick`) и sudo.

Окружение, в котором получены все цифры: Linux 6.18.49-1-MANJARO, Xray 26.3.27 (go1.26.1),
curl 8.22.0 (с ngtcp2/nghttp3), amneziawg-tools v1.0.20260618, Python 3.14.7.
Прогоны — 16 сентября 2026 года.
