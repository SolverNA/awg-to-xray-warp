# WARP через Xray с обфускацией в стиле AmneziaWG

Перенос рабочего конфига AmneziaWG (подключение к Cloudflare WARP) на ядро Xray с сохранением
обфускации, которая обходит блокировку WireGuard российским ТСПУ.

Исследование закончено, рабочий результат есть. Репозиторий содержит и готовый конфиг, и протокол
проверок: какими цифрами что подтверждено, какие гипотезы опровергнуты и чем именно. Вторая часть
важнее первой: рецепт со временем сломается, понимание останется.

Все цифры получены 16 и 17 сентября 2026 года, один регион, один оператор мобильной связи
(Мегафон через тетеринг iPhone) и один домашний WiFi.

---

## 1. Итог

Перенос возможен и работает. Обфускация AmneziaWG сводится к набору junk-пакетов, а их Xray умеет
воспроизводить точно через `noises` у аутбаунда `freedom`.

### Рабочая база

| параметр | значение | чем подтверждено |
|---|---|---|
| endpoint | `162.159.192.1:500` | `:2408` на том же адресе даёт 4 инициации хендшейка и 0 ответов |
| MTU | `1280` | при `1420` хендшейк проходит (1/1), данные не идут |
| keepAlive | `5` | как persistent keepalive у исходного AWG-конфига |
| noise #1 | `hex`, настоящий QUIC Initial, 1252 байта, `delay` `1-2` | без него тот же конфиг проваливается |
| noise #2..#9 | 8 × `rand`, размер `23-911`, `delay` `1-3` | соответствует `Jc=120`, `Jmin=23`, `Jmax=911` из AWG |
| ключ WARP | любой живой | фактор ключа проверен и исключён |

Готовые файлы в корне: `warp-xray.json` (с локальными inbound'ами SOCKS 10808 и HTTP 10809) и
`warp-xray-client.json` (то же без `inbounds`, для импорта в мобильный клиент). Оба собраны
генератором и содержат свой сгенерированный QUIC Initial, а не чужую константу.

### Как пользоваться

Свежий конфиг со своим уникальным QUIC-пакетом:

```sh
./gen-warp-config.py > my-warp.json                 # клиентский конфиг (без inbounds)
./gen-warp-config.py --full --out warp-xray.json    # с inbounds socks/http для десктопа
./gen-warp-config.py --sni mail.ru --seed 42        # воспроизводимая сборка
./gen-warp-config.py --creds my-warp.conf           # свои креды из WireGuard-конфига
```

Генератор берёт проверенную базу из таблицы выше, а hex-пакет каждый раз собирает заново через
`tests/gen-quic-initial.py`: новый DCID, новый ClientHello, настраиваемый SNI. По умолчанию он
прогоняет результат через `xray run -test` (отключается флагом `--no-test`).

На десктопе:

```sh
xray run -c ./warp-xray.json
curl -s -x socks5h://127.0.0.1:10808 https://www.cloudflare.com/cdn-cgi/trace
# ожидается строка warp=on
pkill -f 'xray run -c .*warp-xray.json'
```

URL проверки пишется без завершающего слеша: на `.../cdn-cgi/trace/` Cloudflare отдаёт 404, и
измеритель начинает врать (раздел 11).

В мобильные клиенты на ядре Xray (v2rayTun, Throne, Happ, Hiddify) импортируется
`warp-xray-client.json` или вывод `./gen-warp-config.py`. Два ограничения:

1. Нужен именно JSON. Обфускация держится на hex-пакете размером 1252 байта, а формат
   `wireguard://` его никуда не укладывает, поэтому share-ссылкой профиль не раздать.
2. Ядро клиента должно поддерживать `noises` у freedom-аутбаунда. Если не поддерживает, конфиг
   импортируется без единой ошибки (парсер нестрогий, раздел 2), просто обфускации не будет.

Импорт в клиенты живьём не проверялся, см. раздел 13.

### Схема связки

```
приложение
    │  SOCKS 127.0.0.1:10808 / HTTP 127.0.0.1:10809
    ▼
outbound "warp"   (protocol: wireguard, MTU 1280, endpoint 162.159.192.1:500, keepAlive 5)
    │  streamSettings.sockopt.dialerProxy = "noise-out"
    ▼
outbound "noise-out"  (protocol: freedom)
    │  при создании UDP-сокета шлёт noises:
    │    1 × hex   — настоящий QUIC Initial (1252 б), delay 1-2
    │    8 × rand  — мусор 23..911 байт, delay 1-3
    ▼
UDP → Cloudflare WARP
```

## 2. Что умеет и чего не умеет Xray

Проверялся Xray 26.3.27 (go1.26.1).

**Полей AmneziaWG в ядре нет вообще.** Поиск по бинарю строк `jc`, `jmin`, `jmax`, `s1`, `s2`,
`h1`..`h4`, `i1`, `i2`, `itime`, `junk` даёт 0 вхождений. Есть только `noise`/`noises`.
Wireguard-аутбаунд Xray это обычный WireGuard без AWG-расширений.

**`xray run -test` не доказывает поддержку поля.** JSON-парсер нестрогий и молча глотает
неизвестные ключи. Проверено подстановкой заведомо несуществующего поля:

```json
"zzz_fake_field_12345": 777
```

`xray run -test` ответил `Configuration OK`. Практический вывод: найденный в интернете «конфиг Xray
с полями Jc/Jmin/Jmax» проходит `-test` ровно потому, что эти поля выброшены при разборе.
Единственная проверка это реальный трафик.

**Обратный пример, что `noises` разбирается по-настоящему:** поле `type` валидируется. На
`"type": "bogusType"` ядро отвечает `Invalid packet, only rand/str/hex/base64 are supported`.
Именно `type: "hex"` и позволил воспроизвести junk-пакеты AWG байт в байт.

Прочее, что выяснилось про ядро:

| факт | следствие |
|---|---|
| конфиг без секции `inbounds` принимается (`core: Xray 26.3.27 started`) | клиентский вариант конфига валиден |
| нативный `xray` не умеет tun | для системного туннеля нужен `tun2socks` или клиент-обёртка |
| при `loglevel: info` строки `Sending handshake initiation` и `Received handshake response` не пишутся | счётчики хендшейков доступны только на `debug` |
| hex-пакет не помещается в ссылку `wireguard://` | раздавать можно только полным JSON |

## 3. Соответствие полей AWG и Xray

| поле AWG | что делает | эквивалент в Xray |
|---|---|---|
| `I1`, `I2` | отправить конкретный пакет до хендшейка | `noises: [{"type":"hex","packet":"<hex>"}]` |
| `Jc` | сколько junk-пакетов слать | количество элементов `{"type":"rand"}` |
| `Jmin`/`Jmax` | диапазон размера junk-пакета | `"packet": "Jmin-Jmax"` |
| `S1`..`S4` | добавить junk внутрь самих WG-пакетов хендшейка | нет эквивалента |
| `H1`..`H4` | подменить типы сообщений WireGuard | нет эквивалента |
| `MTU` | MTU интерфейса | `settings.mtu` у wireguard-аутбаунда |
| `Endpoint` | адрес пира | `peers[0].endpoint` |

Отсутствие `S` и `H` здесь не помешало: во всех образцах `H1-H4 = 1,2,3,4` (дефолт, подмены нет) и
`S1..S4 = 0`. Вся обфускация живёт в junk-пакетах. Конфиг с ненулевыми `S`/`H` перенести на Xray
было бы нельзя.

### Ключевое архитектурное отличие и главный теоретический риск

AmneziaWG привязывает `I1` к **каждому пакету хендшейка**: перед каждой инициацией уходит junk.
Xray отправляет `noises` **один раз, при создании UDP-сокета**, и дальше сессия идёт без них.

Отсюда риск: WireGuard переустанавливает сессию примерно раз в две минуты, и если ТСПУ
переклассифицирует флоу по второму хендшейку, не прикрытому noise, то туннель должен отваливаться
через пару минут после старта.

**Риск проверен и не выстрелил.** Рехендшейк переживается без повторной отправки noise, доказано
трижды:

| прогон | сеть | хендшейков отпр./получ. | результат |
|---|---|---|---|
| первый живой прогон SIP-профиля, 5 минут | проводной | 3 / 3 | `warp=on` всё время, `Handshake did not complete` 0 |
| `ref-quic`, фаза стабильности 160 с | WiFi | 3 / 2 | OK=8, FAIL=0 |
| `ref-quic`, фаза стабильности 160 с | Мегафон | 2 / 2 | OK=8, FAIL=0 |

Тайминги трёх хендшейков первого прогона: `01:49:00` ответ за 120 мс, `01:51:02` за 13 мс,
`01:53:03` за 7 мс (`results/xray.log`).

Оговорка про интерпретацию: если бы все QUIC-варианты провалились, это не опровергло бы вывод про
профиль пакета, потому что причиной могла быть именно разница реализаций AWG и Xray. Эту развилку
закрыл этап 6 (раздел 5): нативный AmneziaWG на тех же образцах ведёт себя точно так же, как
Xray-реплики.

## 4. Разбор эталонных `I1`

У всех работавших AWG-образцов `I1` это структурно валидный QUIC Initial v1, у неработавшего
текстовый SIP. Пакеты разобраны анализатором на `cryptography` 50.0.1: ключи выведены по RFC 9001
§5.2 из DCID (salt `38762cf7f55934b34d179ae6a4c80cadccbb7f0a`, метки `client in`, `quic key`,
`quic iv`, `quic hp`), снята header protection, payload расшифрован AES-128-GCM.

| поле | `megafon-ok-500-jc120.conf` | `megafon-ok-1180.conf` | `megafon-ok-903.conf` |
|---|---|---|---|
| размер, байт | 1252 | 1250 | 1250 |
| первый байт (под HP) | `0xc2` | `0xc7` | `0xce` |
| version | `00000001` | `00000001` | `00000001` |
| длина DCID | 20 | 8 | 8 |
| DCID | `19fa4b…eeec` | `09a1ed4edbbe7615` | `97a297ecc34cd6dd` |
| длина SCID / длина token | 0 / 0 | 0 / 0 | 0 / 0 |
| length-varint | 1222 (2 байта) | 1232 (2 байта) | 1232 (2 байта) |
| длина сошлась | да (30 + 1222) | да (18 + 1232) | да (18 + 1232) |
| HP снялась, первый байт после | да, `0xc1` | да, `0xc0` | да, `0xc0` |
| reserved / pn_len / packet number | 00 / 2 / 0 | 00 / 1 / 1 | 00 / 1 / 1 |
| AEAD-расшифровка | OK, 1204 байта | OK, 1215 байт | OK, 1215 байт |
| фреймы | PADDING 925 + CRYPTO(0, 275) | PING + PADDING + CRYPTO(0, 183) + CRYPTO(183, 106) | CRYPTO × 6 фрагментов + PADDING + PING |
| SNI | `www.google.com` | `mail.ru` | `apteka.ru` |
| ALPN | `h3` | `h3` | `h3` |
| TLS | 0x0303, supported_versions 0x0304, шифры 1301/1302/1303 | то же | то же |

Отсюда несколько вещей.

**Это настоящие перехваченные пакеты, а не имитация.** AEAD-тег сошёлся у всех трёх, внутри
лежит валидный TLS ClientHello. Рабочая обфускация маскирует начало сессии под HTTP/3-соединение
браузера, а не под VoIP-звонок.

**`ok-903` и `ok-1180` это дампы живого браузера.** В `ok-903` CRYPTO-фрейм нарезан на 6
фрагментов с перемешанными офсетами `0 / 236 / 266 / 275 / 283 / 290`, которые покрывают
ClientHello целиком без дыр и разбавлены PING. Это известная анти-DPI техника клиента.

**`ok-500` это публичная константа.** Пакет проще (один CRYPTO плюс PADDING), набор extensions
(`ec_point_formats`, `renegotiation_info`, `extended_master_secret`, SCT) характерен для стека
OpenSSL/BoringSSL, а сам конфиг выдан скриптом
`bash-warp-generator`, где `I1` захардкожен на строке 53 (раздел 5, этап 7).

**Неработавший образец.** В `megafon-fail-946-sip.conf` поля `I1`/`I2` это дословный пример из
RFC 3261 §24.2, до последнего байта: `bob@biloxi.com`, `alice@atlanta.com`,
`branch=z9hG4bK776asdhds`, `tag=1928301774`, `Call-ID: a84b4c76e66710@pc33.atlanta.com`,
`CSeq: 314159`. Магический префикс `z9hG4bK` обязателен по §8.1.1.7 и в нашем генераторе сохранён.

**DCID в готовом чужом пакете менять нельзя**: от него выводятся ключи, и правка DCID превращает
валидный пакет в невалидный. Свой пакет нужно генерировать целиком, вместе с криптой.

### Почему старый синтетический QUIC не работал

Ранняя функция `make_quic_initial()` (в `tests/retest-megafon.sh`) собирала «похожий на QUIC»
пакет, который проваливался на Мегафоне с результатом 4 инициации и 0 ответов. Разбор дал шесть
отличий от настоящего пакета, три из них фатальные.

| # | отличие | последствие |
|---|---|---|
| 1 | payload из чистого `random.getrandbits(8)` | при расшифровке Initial-ключами `InvalidTag`. **Фатально** |
| 2 | первый байт строился как `0xC0 \| getrandbits(4)` мимо HP-маски | reserved-биты после снятия HP не нулевые примерно в 75 % случаев, по RFC 9000 §17.2 это `PROTOCOL_VIOLATION`. **Фатально** |
| 3 | `pn_len` рассогласован с номером пакета | маска давала `pn_len=3` и `pn=6110100`, невозможный номер для первого пакета соединения. **Фатально** |
| 4 | фреймов нет вообще | внутри нечего разбирать |
| 5 | DCID и payload независимы | ключи не связаны с содержимым |
| 6 | header protection не накладывалась | пакет не соответствует RFC на уровне заголовка |

Снаружи всё было скопировано верно: version, пустые SCID и token, сходящийся length-varint,
правильный размер. **Ловушка:** именно поэтому пакет проходил собственный структурный чекер
`awg_parse()`, который смотрел только заголовок. Чекер, который не проверяет расшифровку,
для QUIC бесполезен.

Действующий `tests/gen-quic-initial.py` делает всё по RFC: случайный DCID, вывод Initial-ключей,
настоящий TLS ClientHello с SNI и ALPN, CRYPTO-фрейм, PADDING, AES-128-GCM, header protection.
Флаг `--self-test` генерирует пакет и разбирает его обратно.

## 5. Хронология экспериментов

### Этап 1. Что умеет Xray

Раздел 2. Итог: архитектура переноса это outbound `wireguard` со
`streamSettings.sockopt.dialerProxy`, указывающим на outbound `freedom` с `noises`.

### Этап 2. Первый перенос (SIP-профиль) и первые живые прогоны на проводном

Исходный AWG-конфиг `legacy/WARPv3_77.conf`: `H1-H4 = 1,2,3,4`, `S1-S4 = 0`, `I1` = SIP INVITE из
RFC 3261 (348 байт), `I2` = SIP 100 Trying (245 байт), `Jc=4`, `Jmin=40`, `Jmax=70`. Перенесён в
то, что сейчас лежит как `legacy/warp-xray-sip-profile.json`.

Первый пятиминутный прогон (`results/xray.log`): `warp=on`, внешний IPv4 `104.28.230.246`,
IPv6 `2a09:bac5:5150:2373::388:46`, задержка 61 мс, скорость 6.51 MB/s (54.6 Мбит/с, 9.5 МБ за
1.46 с), три хендшейка с ответами за 120, 13 и 7 мс, 17 keepalive подряд, ни одного
`Handshake did not complete`. Две строки `failed to handle UDP input > io: read/write on closed
pipe` безобидны, это закрытие UDP-сессии после DNS-теста.

A/B тест (`tests/test-warp.sh`, отчёт `results/test-report.txt`):

| | вариант A, с `noises` | вариант B, тот же конфиг без `noises` |
|---|---|---|
| результат | `warp=on` | ни одного ответа |
| запросы | 9/9 успешных за 161 с | все curl в таймаут |
| хендшейки | 2 отправлено / 2 ответа | 10 отправлено / 1 ответ |
| `Handshake did not complete` | 0 | 8 |
| задержка | 49 мс | нет |
| скорость | 6.42 MB/s (53.9 Мбит/с), 9.5 МБ за 1.49 с | нет |

Первый хендшейк B прошёл за 95 мс, после чего пошло
`Retrying handshake because we stopped hearing back after 15 seconds`, всего 3 таких строки.

Вывод этапа: на проводном ТСПУ режет чистый WireGuard, обфускация необходима, и Xray её
воспроизводит.

Матричный тест (`tests/test-megafon.sh`, отчёт `results/megafon-report.txt`), счётчики в формате

### Этап 4. Ретест с изоляцией переменных

В матрице этапа 3 менялось по несколько параметров сразу. Ретест (`tests/retest-megafon.sh`,
отчёт `results/retest-report.txt`) построен так, что каждый вариант отличается от базы ровно одним
параметром.

Сначала из уравнения убран ключ: все три регистрации WARP проверены живьём на рабочей сети.

| ключ | ответ |
|---|---|
| `p1Fqp…` | `warp=on`, `ip=104.28.197.9` |
| `IFkdR…` | `warp=on`, `ip=104.28.197.9` |
| `WE7c0…` (из июльского `legacy/old-warp-xray.json`) | `warp=on`, `ip=2a09:bac5:27bd:1b4b::2b8:1a` |

Доступность endpoint'ов на голом WireGuard без обфускации (Мегафон, один ключ, один MTU): FAIL у
всех пяти, но двумя разными способами.

| endpoint | хендшейк отпр./получ. | что это значит |
|---|---|---|
| `162.159.192.1:500` | 4 / 0 | ответа на хендшейк нет вовсе |
| `162.159.192.1:2408` | 4 / 0 | то же |
| `8.6.112.7:946` | 2 / 1 | хендшейк прошёл, душится установленная сессия |
| `8.34.146.7:1180` | 2 / 1 | то же |
| `8.34.70.4:903` | 2 / 1 | то же |

Матрица с изоляцией. База это QUIC-`I1` из `ok-500` + 8 × rand `23-911` + `162.159.192.1:500` +
MTU 1280:

| вариант | отличие от базы | результат | хендшейк | время |
|---|---|---|---|---|
| 3.1 (база) | нет | **OK**, `warp=on` | 1 / 1 | 0.393589 с |
| 3.2 | только порт: `:500` → `:2408` | FAIL | 4 / 0 | таймаут |
| 3.4 | только hex: чужой `I1` → свой синтетический QUIC | FAIL | 4 / 0 | таймаут |
| 3.5 | только hex: QUIC → SIP (RFC 3261) | FAIL | 4 / 0 | таймаут |
| 3.6 | только MTU: 1280 → 1420 | FAIL | 1 / 1 | таймаут |
| 3.3 | полная реплика `ok-1180` (ep `8.34.146.7:1180`, MTU 1420) | FAIL | 1 / 1 | таймаут |

Стабильность варианта 3.1: 5 запросов из 5 за ~100 с, время ответа от 0.24 до 0.79 с.

Про вариант 3.4 важно: он опроверг не «свой пакет», а «пакет без настоящей крипты внутри». Разбор
этого пакета в разделе 4, окончательное опровержение более широкой формулировки в этапе 9.

### Этап 5. Природа проверки QUIC

Ключи шифрования QUIC Initial выводятся из DCID по фиксированному публичному алгоритму (RFC 9001).
DPI видит DCID в открытом виде, выводит те же ключи, расшифровывает Initial-пакет и ждёт внутри
валидный TLS ClientHello. Пакет со случайным payload эту проверку не проходит, флоу режется ещё до
хендшейка, отсюда 4/0 у варианта 3.4.

На этом этапе из результата был сделан более широкий вывод («свой сгенерированный QUIC не
работает, нужно копировать чужой»). Он опровергнут этапом 9: работает любой пакет, который
корректно расшифровывается, включая свой. Правильная формулировка: не работает **синтетика без
крипты**.

### Этап 6. Нативный AmneziaWG как базовая истина

Чтобы понять, виноват ли перенос на Xray, те же образцы подняты родным `awg-quick`
(`tests/retest2.sh`, отчёт `results/retest2-report.txt`).

| конфиг | нативный AWG | Xray-реплика |
|---|---|---|
| `megafon-ok-1180.conf` | FAIL | FAIL (вариант 3.3) |
| `megafon-ok-903.conf` | FAIL | отдельно в Xray не гонялся |
| `megafon-ok-500-jc120.conf` | **OK**, `warp=on` | **OK** (вариант 3.1) |

**Xray-реплики ведут себя точно так же, как оригиналы в родном AmneziaWG.** Дефекта переноса нет.
Конфиги на `8.34.x` просто умерли с того момента, когда пользователь их последний раз проверял.

Отдельно проверено, что рецепт не привязан к ключу из образца: с рабочим профилем на Мегафоне и
`IFkdR`, и `p1Fqp` дают `warp=on`, хендшейк 1/1 у обоих (`results/retest2-IFkdR-control.log`,
`results/retest2-p1Fqp-test.log`).

### Этап 7. Откуда взялся рабочий пакет

Конфиг `megafon-ok-500-jc120.conf` выдан генератором
`https://raw.githubusercontent.com/ImMALWARE/bash-warp-generator/main/warp_generator.sh`. Разбор
скрипта (132 строки):

- он генерирует пару ключей (`wg genkey`) и регистрирует устройство в Cloudflare API
  (`api.cloudflareclient.com/v0i1909051800`: `POST /reg` с `type: ios`, затем `PATCH reg/<id>` с
  `warp_enabled: true`);
- `I1` захардкожен константой на **строке 53**, `Endpoint = 162.159.192.1:500` на **строке 60**, а
  строка, которая брала endpoint из ответа API, закомментирована на **строке 35**.

Отсюда: все конфиги от этого скрипта несут один и тот же QUIC-пакет и один и тот же endpoint,
перегенерация даёт свежие креды, но не новый `I1`. Образцы `ok-1180` и `ok-903` с другим `I1` и
адресами `8.34.x` пришли из другого источника, который endpoint из API всё-таки читал.

Риск понятен: публичная константа массового скрипта рано или поздно попадёт в сигнатуры, и профиль
отвалится разом у всех, ровно как уже случилось с SIP-пакетом из RFC 3261.

**Поэтому написан генератор**, который собирает настоящий QUIC Initial с нуля
(`tests/gen-quic-initial.py`), и готовый прод-конфиг теперь собирается им же
(`./gen-warp-config.py`). Вариант «снять свой дамп через `tcpdump` + `curl --http3`» рассмотрен и
сознательно отвергнут: `sudo` требует пароль, а генерация с нуля даёт новый пакет с настраиваемым
SNI при каждом запуске. Возвращаться к нему смысла нет.

### Этап 8. Проверка прод-профиля на домашнем WiFi

Прогон `tests/test-wifi.sh` (отчёт `results/wifi-report.txt`), сеть `wlo1 192.168.0.15/24`,
дефолт через `192.168.0.1`, собственный VPN пользователя выключен.

| вариант | что это | результат | хендшейк |
|---|---|---|---|
| A | прод-профиль: QUIC `I1` + `162.159.192.1:500` + MTU 1280 | **OK**, `warp=on`, ip `104.28.198.244`, стабильность 5/5 за 100 с | 1 / 1 |
| B | старый SIP-профиль: `8.6.112.7:946` + MTU 1420 | **OK**, `warp=on`, ip `2a09:bac1:6180::407:1f` | 1 / 1 |
| C | контроль: чистый WG без обфускации, тот же endpoint и MTU, что у A | **FAIL**, ни одного ответа | **7 / 0** |

Вариант C самая важная строка: без него нельзя отличить «обфускация работает» от «на этой сети

вывода этапа 2, полученное спустя примерно 19 часов и на другом endpoint'е.

### Этап 9. Сравнение пяти noise-профилей, решающий эксперимент

Скрипт `tests/test-profiles.sh` собирает пять конфигов с **одинаковой** базой
(`162.159.192.1:500`, MTU 1280, ключ `p1Fqp`, 8 × rand `23-911`) и различием **только** в

это стабильность 160 секунд с запросом каждые 20 секунд, чтобы поймать рехендшейк.

Профили:

| профиль | что в hex |
|---|---|
| `ref-quic` | чужой перехваченный `I1` из `megafon-ok-500-jc120.conf` |
| `gen-quic` | свой сгенерированный QUIC Initial (`tests/gen-quic-initial.py`) |
| `old-sip` | дословный SIP из RFC 3261, тот самый публичный текст |
| `peer-sip` | рандомизированный SIP из рабочего конфига знакомого (`awg-samples/peer-sip-randomized.json`) |
| `gen-sip` | свой сгенерированный рандомизированный SIP (`tests/gen-sip-invite.py`) |

**Мобильный прогон** (`results/profiles-report-mobile.txt`), 2026-09-17 00:46, тетеринг iPhone,
`172.20.10.2/28`, шлюз `172.20.10.1`. Фаза 1:

| профиль | hex, байт | результат | задержка | скорость | хендшейк |
|---|---|---|---|---|---|
| `ref-quic` | 1 × 1252 | **OK**, `warp=on`, ip `104.28.230.244` | 0.227 с | 3.80 MB/s (31.9 Мбит/с) | 1 / 1 |
| `peer-sip` | 2 × 396, 276 | FAIL (curl rc=28) | нет | нет | **7 / 0** |
| `gen-sip` | 2 × 348, 244 | FAIL (curl rc=28) | нет | нет | **7 / 0** |

Фаза 2 на мобильной: `ref-quic` дал OK=8, FAIL=0, задержку 0.195 с, 2.90 MB/s (24.3 Мбит/с) и
хендшейк 2 / 2, то есть рехендшейк пережит. `peer-sip` снова FAIL, 7 / 0.

| профиль | результат | задержка | скорость | хендшейк |
|---|---|---|---|---|
| `ref-quic` | OK | 0.235 с | 3.42 MB/s (28.7 Мбит/с) | 1 / 1 |
| `peer-sip` | OK | 0.221 с | 4.39 MB/s (36.8 Мбит/с) | 1 / 1 |
| `gen-sip` | OK | 0.181 с | 2.96 MB/s (24.8 Мбит/с) | 1 / 1 |
| `gen-quic` | OK | 0.226 с | 2.58 MB/s (21.6 Мбит/с) | 1 / 1 |
| `old-sip` | OK | 0.282 с | 2.87 MB/s (24.1 Мбит/с) | 1 / 1 |

## 6. Что установлено про поведение ТСПУ

### Три различимых режима, а не два

| режим | сигнатура счётчиков | где наблюдался |
|---|---|---|
| хендшейк не проходит вовсе, флоу режется до него | 4 / 0 | голый WG на `:500` и `:2408` (этап 4) |
| то же, с более агрессивным ретраем | 7 / 0 | все SIP-профили на Мегафоне (этап 9), голый WG на WiFi (этап 8, вариант C) |
| хендшейк проходит, данные душат | 2 / 1 | голый WG на `8.6.112.7:946`, `8.34.146.7:1180`, `8.34.70.4:903` (этап 4) |
| то же при неверном MTU | 1 / 1 | вариант 3.6, MTU 1420 (этап 4) |

Отсюда правило измерения: **ответ на хендшейк сам по себе ничего не доказывает**. Критерий успеха
ровно один, получен ли `warp=on`.

### Что решает и что нет

| фактор | влияет | доказательство |
|---|---|---|
| ключ / регистрация WARP | нет | все три ключа дают `warp=on`; рабочий профиль работает и на `IFkdR`, и на `p1Fqp` |
| endpoint и порт | да | `:500` OK, `:2408` на том же адресе FAIL (3.1 против 3.2) |
| MTU | да | 1280 OK, 1420 FAIL при всём прочем равном (3.1 против 3.6) |
| содержимое hex-пакета | да | QUIC OK, SIP FAIL на одинаковой базе (этап 9) |
| наличие обфускации вообще | да | мобильная: голый WG FAIL, с QUIC OK; WiFi: голый WG 7/0 FAIL, тот же endpoint с обфускацией OK |
| объём rand-мусора сам по себе | нет | 8 × rand без hex-пакета FAIL (вариант 10) |
| тип сети | для SIP-профиля да, для QUIC нет | SIP: WiFi OK, Мегафон FAIL; QUIC OK на обеих |

Про порт есть объяснение, которое остаётся гипотезой: 500 это IKE/IPsec, мобильные операторы
обычно пропускают его как корпоративный VPN, а нестандартные 946, 1180 и 903 режут. Отдельно это
не проверялось.

Про MTU причина не установлена. Похоже на срез по размеру пакета или на проблему фрагментации в
мобильной сети, но прямо это не измерялось.

### Главный вывод про природу фильтра

**ТСПУ реально разбирает QUIC Initial по RFC 9001, а не держит байтовый whitelist известных
пакетов.** Доказательство: `gen-quic` со случайным DCID, своим ClientHello и своим SNI, которого не
существовало ни в одной базе, прошёл Мегафон на базе, идентичной эталонной, и дал результат того же
порядка (0.238 с против 0.227 с у `ref-quic`).

Значит проверяется структура и расшифровываемость, а не совпадение с образцом. Практическое
следствие: **ротация пакета безопасна**, от чужой публичной константы можно и нужно уходить. Именно
поэтому `gen-warp-config.py` генерирует новый `I1` при каждом запуске.

### SIP мёртв на мобильной как класс, а не как текст

На одинаковой базе легли все три варианта: `old-sip` (дословный RFC 3261), `peer-sip`
(рандомизированный, из чужого рабочего конфига) и `gen-sip` (наш генератор). Все три 7 / 0.
Режется сам признак «UDP на порт 500 с SIP-подобной нагрузкой», а не конкретный известный текст.
Легитимность и уникальность SIP-сообщения роли не играют, направление закрыто.

### Ужесточение во времени

Июльский профиль `legacy/old-warp-xray.json`: ключ `WE7c0`, `162.159.192.1:500`, MTU 1280,
8 × rand `23-911` и **ноль hex-пакетов** (при конвертации из `ok-500` потеряли `I1`). По словам
владельца, в июле он на Мегафоне работал. В сентябре ровно такой профиль это вариант 10 матрицы
этапа 3, и он FAIL. Требования к обфускации за два месяца выросли: раньше хватало rand-мусора,
теперь нужен валидный QUIC Initial.

### Как воспроизвести

Скрипты запускаются из любого каталога и сами переходят в корень репозитория:

```sh
./tests/test-warp.sh          # A/B: обфускация против её отсутствия
./tests/test-megafon.sh       # матрица из 10 профилей
./tests/retest-megafon.sh     # матрица с изоляцией переменных (для нативного этапа нужен sudo)
./tests/retest2.sh            # нативный awg-quick; --awg-only пропускает Xray-часть
./tests/test-wifi.sh          # прод-профиль на проводном/WiFi + контроль без обфускации
./tests/test-profiles.sh      # сравнение пяти noise-профилей на одной базе
```

`test-profiles.sh` сам определяет тип сети по шлюзу (`172.20.10.x` считается мобильной) и пишет
файлы с тегом `mobile` или `wifi`, а прошлый комплект того же тега переименовывает в
`*-<тег>-ГГГГММДД-ЧЧММ.<расш>`. Остальные скрипты перезаписывают свой отчёт в `results/`.

Требуется: `xray` (проверялось на 26.3.27), `curl`, `python3` с пакетом `cryptography` (для
генератора QUIC), для нативных тестов `amneziawg-tools` (`awg-quick`) и sudo.

Окружение, в котором получены все цифры: Linux 6.18.49-1-MANJARO, Xray 26.3.27 (go1.26.1),
curl 8.22.0 (с ngtcp2/nghttp3), amneziawg-tools v1.0.20260618, Python 3.14.7,
cryptography 50.0.1.

## 9. Политика анонимизации

Репозиторий публичный, и состав публикуемых данных выбран сознательно.

| категория | решение |
|---|---|
| пути вида `/home/<user>/...`, имя пользователя в путях | затираются, заменяются относительными или `<repo>` |
| путь scratchpad `/tmp/...` в отчётах | заменяется на `<tmp>` |
| hostname машины | заменяется на `<host>` |
| реальный внешний адрес роутера пользователя | затирается, если всплывёт |
| выходные адреса Cloudflare (`104.28.*`, `2a09:bac*`) | **остаются**: это не адрес пользователя |
| локальные адреса (`192.168.*`, `172.20.10.*`, `172.19.*`, `fe80::*`, `docker0`) | остаются |
| все данные WARP: `PrivateKey`, peer `PublicKey`, endpoint, `172.16.0.2`, IPv6, MTU, DNS | **остаются по решению владельца**, включая приватные ключи |
| обфускация целиком: `Jc/Jmin/Jmax`, `S1-S4`, `H1-H4`, hex `I1`/`I2` | остаётся, это предмет исследования |
| сведения о системе (ядро, версии Xray, curl, python) | остаются, нужны для воспроизводимости |
| скрипты, отчёты, тайминги, скорости, логи хендшейков | остаются |

Про приватные ключи владелец предупреждён отдельно: они не деанонимизируют, но позволяют поднять
туннель на его регистрации WARP. Решение публиковать принято им осознанно. Email в коммитах
заменён на `SolverNA@users.noreply.github.com`.

**Чистка логов.** Сырые debug-логи Xray содержат домены и коннекты пользователя, в репозиторий они
не попадают. Логи в `results/` пропущены через whitelist-фильтр, оставляющий только старт ядра и
события WireGuard (хендшейки, keepalive, ошибки транспорта):

| файл | было строк | стало строк |
|---|---|---|
| `results/xray-A.log` | 1350 | 112 |
| `results/xray-B.log` | 173 | 125 |
| `results/xray.log` | 290 | 121 |

Счётчики хендшейков сверены до и после фильтрации и совпали точь-в-точь: A 2/2/0, B 10/1/8 плюс 3
`Retrying handshake`, `xray.log` 3/3/0, keepalive 5 и 17. Оставшиеся в логах доменные имена это
содержимое SIP-noise из конфига (`pc33.atlanta.com`, `biloxi.com`, `atlanta.com`), одно упоминание
`www.cloudflare` в `xray-B.log` как ключевое доказательство отвала варианта B, и имена файлов
конфигов.

## 10. Что осталось непроверенным

Перечислено честно, чтобы никто не принял эти пункты за закрытые.

- **Роль SNI не изолирована.** Предлагалось прогнать `gen-quic --sni www.google.com` против
  `--sni example.org` на одинаковой базе. Не прогонялось, влияет ли имя в ClientHello на решение
  ТСПУ, неизвестно.
- **Фрагментация CRYPTO-фрейма не реализована** в `tests/gen-quic-initial.py`. У `ok-903` и
  `ok-1180` ClientHello нарезан на фрагменты, у нас идёт одним куском. Простой вариант прошёл,
  поэтому до этого не дошло.
- **Совпадение размера 1252 байта с портом 500 не изолировано.** Оба параметра менялись только
  вместе с рабочей базой, и вклад каждого по отдельности не измерен.
- **Долговременная стабильность неизвестна.** Максимум непрерывной работы в измерениях это 161 с
  на проводном и по 160 с в фазах стабильности. Что происходит через час или три, не проверялось.
- **`gen-quic` не проходил фазу стабильности на мобильной.** Фаза 2 гонялась на `ref-quic` и
  `peer-sip`, поэтому про рехендшейк на своём сгенерированном пакете данных нет.
- **Импорт в клиенты не проверялся живьём.** Ни v2rayTun, ни Throne, ни Happ, ни Hiddify не
  тестировались, вывод про JSON и `noises` сделан из устройства формата и парсера.
- **Один оператор, одна сота, один день.** Все мобильные измерения сделаны через тетеринг одного
  iPhone на Мегафоне 16 и 17 сентября 2026 года. ТСПУ настраивают по-разному в разных регионах и
  перенастраивают со временем, что и показывает история с июльским профилем.
- **Выводы про блокировку целых подсетей сделаны по трём адресам** (`8.6.112.7`, `8.34.146.7`,
  `8.34.70.4`). Возможно, дело в конкретных адресах, а не в подсетях `8.6.x` и `8.34.x` целиком.
- **Причина, по которой MTU 1420 ломает передачу при прошедшем хендшейке, не установлена.**
- **`results/retest2-report.txt` содержит только этап 1.** Этап 2 в нём помечен как пропущенный
  (`--awg-only`), а его фактический результат лежит отдельно в `retest2-IFkdR-control.log` и
  `retest2-p1Fqp-test.log`.

## 11. Грабли инструментов и окружения

Собрано отдельно, потому что на эти вещи наступают повторно, и часть из них портит не запуск, а
именно результаты измерений.

### Измерения

| проблема | причина | как чинится |
|---|---|---|
| 16 ложных FAIL в первом прогоне | URL `https://www.cloudflare.com/cdn-cgi/trace/` со слешем: Cloudflare отдаёт 404 HTML без поля `warp=`, при этом `rc=0` и время 0.057–0.12 с | URL без слеша, определён один раз; в каждую пробу добавлен `http_code` и третий статус `BAD` (HTTP ≠ 200, проблема измерителя) отдельно от `FAIL` (проблема туннеля) |
| счётчиков хендшейков нет в логе | при `loglevel: info` Xray не пишет `Sending handshake initiation` и `Received handshake response` | только `loglevel: debug` |
| `xray run -test` якобы не даёт `Configuration OK` | при debug-логе в stdout идёт строка `app/proxyman/inbound: creating stream worker...`, и `tail -1` ловит её | фильтровать `grep -E 'Configuration OK\|Failed\|error'` |
| WiFi-прогон уничтожил результаты мобильного | все выходные файлы назывались `profiles-report.txt` без тега сети | теги `mobile`/`wifi` по шлюзу, ротация прошлого комплекта в `*-<тег>-<дата>-<время>`, чужой тег не трогается |
| лог фазы 2 затирал лог фазы 1 | мусорный `${stab:+}` в имени файла | отдельное имя `-stability.log` |

### Shell

| проблема | причина | как чинится |
|---|---|---|
| `test-profiles.sh: строка 59: name: не заданы границы переменной` | **bash 5.3** помечает локальными (unset) все имена в составном `local name="$1" stab="$2" cfg="$S/prof-$name.json"` **до** выполнения присваиваний, поэтому `$name` оказывается unbound под `set -u` | объявления `local` отделены от присваиваний |
| в отчётах всегда `rc=0` вместо настоящей ошибки curl | `T=$(curl ...) \|\| true; RC=$?` — `\|\| true` затирал код | порядок переставлен, в FAIL-ветке печатается настоящий `rc=7` или `rc=28` |
| счётчик хендшейков печатался как `0` и ещё раз `0` | `grep -c … \|\| echo 0` при отсутствии совпадений выдаёт ноль от `grep` и ноль от `echo` | `\|\| true` плюс нормализация |
| падение на `[ "$hs_s" -gt 1 ]` | `$(grep -ac ...)` по несуществующему логу возвращает пустую строку | обёртки `${hs_s:-0}` |
| `cleanup()` возвращал ненулевой код из trap на EXIT | `${PID}` без дефолта | `${PID:-}` и явный `return 0` |
| зависимость от `bc` | лишняя | вся плавающая арифметика переведена на `awk` |

Минимальное репро для bash 5.3:

```sh
bash -c 'set -u; f(){ local a="$1" b="X-$a"; }; f q'
# bash: b: unbound variable
```

### Окружение

| проблема | причина | как чинится |
|---|---|---|
| `awg-quick up` → `Error: ipv6: IPv6 is disabled on this device` | IPv6 отключён в системе, а в конфигах есть v6-адрес | из временной копии конфига удаляются IPv6 в `Address`, IPv6 в `DNS` и `::/0` в `AllowedIPs` |
| `awg-quick` → `resolvconf: signature mismatch: /etc/resolv.conf` | конфликт с системным resolvconf | строка `DNS` удаляется целиком (`-e "/^DNS = /d"`); системное лечение `sudo resolvconf -u` |
| `--seed` у `gen-quic-initial.py` не давал воспроизводимости | внутри использовался `os.urandom` | заменён на `random.randbytes` |
| `git rev-parse --abbrev-ref HEAD` сразу после `git init` → `fatal: неоднозначный аргумент «HEAD»` | HEAD не существует до первого коммита | ничего, просто не вызывать до первого коммита |
